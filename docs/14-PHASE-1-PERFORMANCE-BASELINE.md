# Task 1.13 — 多环境订单簿处理性能基线

- 日期：2026-11-26
- 状态：Completed
- 平台：macOS ARM64，Python 3.12.3，PostgreSQL 16
- 工具：`scripts/run_phase1_performance_baseline.py`
- 原始报告：`data/reports/phase1-performance-baseline.json`（本地生成，不提交）

## 1. 目标与边界

本基线测量当前“单模拟环境串行处理、环境间流动性隔离”架构在 1、3、5、10、20 个活跃环境下的成本。测试使用确定性 Canonical 订单簿，在真实 PostgreSQL 测试库中运行完整 Dispatcher、Unit of Work、Scheduler、撮合、资金流水、成交和 Portfolio 投影链路。

每个环境提交一笔数量 1、预算 105 USDT、配置延迟 100ms 的市价买单；在 125ms 时执行，因此可预期 Scheduler Lag 为 25ms。预热 2 个订单簿事件后，测量 20 个同样的订单簿更新。不访问外部交易所。

其他结果：

- 各规模 Scheduler Lag 均为 25ms，与确定性时钟预期一致。
- Dispatcher Error 均为 0。
- 当前 Dispatcher 是同步串行入口，没有内部输入队列，因此本测试 Event Queue Backlog 为 0。该数字不代表外部 Feed 在高频输入下永远不会积压。
- 数据库事务数等于 `环境数 × 20`，没有跳过无挂单环境的订单簿流动性更新。
- 事务耗时从 SQLAlchemy `begin` 测量到 `commit` / `rollback`，包含事务内的领域计算，不是纯 PostgreSQL 服务器执行时间。
- RSS 来自进程 High-water Mark，所以不同规模的增量不应解读为线性常驻内存曲线。

## 3. 业务结果一致性

程序对每个环境生成排除随机环境/账户 ID 的业务指纹，比较：

- 订单状态、序列、成交量、剩余量、均价和 Scheduler Lag。
- 成交价格、数量、手续费和 Maker/Taker 角色。
- 可用/冻结余额、持仓数量、平均成本和总成本。
- 剩余 Bid/Ask 流动性和流动性消耗次数。

结果：所有环境内一致，且 1 / 3 / 5 / 10 / 20 规模均与单环境业务指纹一致。无负余额、超额成交、重复成交或重复流动性消耗。

## 4. 决策

实测确认订单簿每事件耗时随环境数近似线性增长，20 环境下平均约 106ms。这与已接受的 Phase 1 Known Limitation 一致；在真实高频订单簿下，多环境可能形成 Feed 积压。

当前不启动会改变路径依赖流动性、环境隔离或事件顺序的优化，也不设置未经真实 Feed 验收的硬性指标。Phase 1 继续保留当前串行语义，将多环境高频处理作为技术债跟踪。
