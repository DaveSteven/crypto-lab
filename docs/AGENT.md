# AGENTS.md

## 1. Project Context

### 1.1 项目名称

Crypto Lab

### 1.2 项目定位

基于真实虚拟货币市场数据的个人模拟交易与量化研究平台。

项目核心目标为：

- 金融知识学习。
- 真实市场数据分析。
- 虚拟资金模拟交易。
- 跨交易所套利研究。
- 历史行情回放。
- 量化策略验证。
- 交易风险分析。

项目不以短期盈利为首要目标。

### 1.3 当前开发阶段

**Phase 0-A 已完成；Phase 0-B 与 Phase 1 可并行推进**

Phase 0-A 已验证 API 可用性、数据正确性、短时采集及价差计算。

Phase 0-B 继续负责长期稳定性、延迟统计及套利机会研究。Phase 0-B 未经验收时，不得将长期稳定性或套利研究标记为完成，但不阻塞 Phase 1 基础开发。

Phase 1 仅可在已确认范围内开发基础模拟交易功能，不得借此扩展至真实交易或其他非项目范围。

## 3. Development Workflow — 开发流程

### 3.1 开发前检查

每次开始任务前必须：

- 确认当前开发阶段。
- 阅读相关需求及技术文档。
- 确认当前任务的范围及验收标准。
- 检查 Git 工作区状态。
- 检查当前分支。
- 检查现有代码及测试。
- 确认是否存在未提交的用户修改。
- 确认是否已有可复用的模块。
- 确认任务依赖及潜在影响。

不得在未检查现有实现的情况下重复创建模块。

### 3.2 任务执行流程

1. 理解需求。
2. 检查现有实现。
3. 制定技术方案。
4. 明确验收条件。
5. 实现最小必要变更。
6. 编写或更新测试。
7. 执行测试。
8. 进行实际运行验证。
9. 更新相关文档。
10. 输出任务总结。

### 3.3 任务范围控制

遵循最小变更原则。

未经确认不得：

- 扩大任务范围。
- 提前实现后续阶段功能。
- 重构与当前任务无关的模块。
- 修改已确认的核心架构。
- 删除现有功能。
- 引入新的大型框架。
- 增加付费服务。
- 修改项目总体目标。

发现额外问题时，应单独记录，不默认扩大当前任务。

### 3.4 决策规则

以下事项可在符合项目规范的前提下自主决定：

- 局部变量命名。
- 内部函数拆分。
- 测试数据组织。
- 非业务性质的代码结构优化。
- 明确的错误修复。

以下事项必须由项目负责人确认：

- 核心数据模型变更。
- 金融计算公式变更。
- 模拟成交规则变更。
- 数据存储架构变更。
- 开发阶段及功能范围变更。
- 新增收费依赖。
- 数据源访问策略变更。
- 接入具有真实交易权限的接口。

## 6. Financial Calculation Rules — 金融计算规范

### 6.1 数值精度

价格、资产数量、手续费、资金余额及收益计算必须使用 Decimal 或经过确认的等价定点精度方案。

不得直接使用 float 作为核心资金计算的数据类型。

从外部 API 接收数值时，应尽可能保留原始十进制表示。

示例：

```python
from decimal import Decimal

price = Decimal("1665.10")
quantity = Decimal("0.5")
amount = price * quantity
```

不得通过 Decimal(float_value) 直接转换浮点数。

如果第三方 SDK 已经将原始数据转换为 float，应记录潜在精度损失，并在必要时保留原始 API 数据。

### 6.2 金额舍入

必须区分：

- 价格精度。
- 数量精度。
- 金额精度。
- 手续费精度。
- 最小下单数量。
- 最小交易金额。

舍入规则必须符合交易所市场配置或明确的模拟规则。

不得使用统一的两位小数处理所有资产。

### 6.3 报价定义

- Bid：当前买方报价。
- Ask：当前卖方报价。
- Best Bid：最高买入报价。
- Best Ask：最低卖出报价。
- Last：最近一次成交价格。

模拟立即买入时，应参考 Ask。

模拟立即卖出时，应参考 Bid。

不得默认使用 Last 作为可执行成交价格。

### 6.4 跨交易所价差

基本毛价差：

```text
gross_spread = sell_bid - buy_ask

gross_spread_rate = gross_spread / buy_ask
```

初步净收益估算：

```text
estimated_net_profit =
    sell_notional
    - buy_notional
    - buy_fee
    - sell_fee
    - execution_cost
    - allocated_rebalance_cost
```

其中：

- buy_notional 为估算实际买入金额。
- sell_notional 为估算实际卖出金额。
- execution_cost 为尚未包含在成交报价中的其他执行成本。
- allocated_rebalance_cost 为分摊至当前实验的资金再平衡成本。

不得重复计算已经包含在订单簿成交均价中的滑点。

所有成本参数必须注明来源、版本及适用条件。

### 6.5 交易对一致性

跨平台比较必须确认：

- 基础资产一致。
- 计价资产一致。
- 市场类型一致。
- 合约或代币身份一致。
- 报价时间具有可比性。

例如：

BTC/USDT 现货与 BTC/JPY 现货不得直接进行价差计算。

BTC/USDT 现货与 BTC/USDT 永续合约不得直接作为同类现货报价比较。

### 6.6 收益定义

必须区分：

- 理论毛价差。
- 估算净收益。
- 模拟成交收益。
- 实际交易收益。

Phase 0 只能产生理论价差及估算结果，不得将其描述为实际成交利润。

## 7. Market Data Integrity — 行情数据真实性

### 7.1 数据来源

所有行情必须能够识别：

- 交易所。
- 市场类型。
- 原始交易对。
- 标准化交易对。
- 数据接口。
- 数据来源时间。
- 本地接收时间。

### 7.2 真实数据与测试数据

必须明确区分以下数据类型：

- LIVE：实时真实行情。
- HISTORICAL：历史真实行情。
- MOCK：人工构造测试数据。
- SYNTHETIC：程序生成的测试数据。

禁止：

- 使用 Mock 数据冒充真实行情。
- 使用随机价格冒充 API 响应。
- 伪造交易所响应。
- 伪造接口测试结果。
- 伪造实验报告。
- 将历史价格描述为当前实时价格。

### 7.3 缺失数据

交易所未提供的数据必须保留为 null 或明确的缺失状态。

不得：

- 自动将缺失价格设置为 0。
- 自动将缺失手续费设置为 0。
- 伪造交易所时间戳。
- 使用其他字段代替缺失字段且不进行标注。

估算值必须注明估算方法。

### 7.4 原始数据保留

在技术验证阶段，应按需保存原始 API 响应。

标准化数据应保留与原始数据的关联信息。

当数据转换失败时，应能够定位对应的原始响应。

原始数据保留策略必须考虑存储容量及数据使用许可。

### 7.5 行情有效性

以下数据不得直接用于套利机会计算：

- 已过期行情。
- 无法确定来源的行情。
- 无效或负数价格。
- 不完整的必要报价字段。
- 时间差超出允许范围的跨平台报价。
- 已检测到顺序异常且尚未恢复的数据流。
- 尚未完成同步的增量订单簿。

行情有效性阈值应通过配置管理，并在实验报告中注明。

## 8. Time Management — 时间规范

### 8.1 时间字段

必须区分：

- exchange_timestamp：交易所提供的事件时间。
- received_timestamp：本地接收时间。
- processed_timestamp：系统处理时间。
- simulation_timestamp：模拟环境时间。

统一使用 UTC 存储。

面向用户展示时，可转换为 Asia/Tokyo。

### 8.2 延迟计算

必须区分：

- REST 请求往返耗时。
- WebSocket 消息接收间隔。
- 本地数据处理耗时。
- 交易所事件时间与本地接收时间的差值。

交易所事件时间与本地接收时间的差值可能受到时钟偏移影响，不得直接认定为精确网络延迟。

耗时测量应优先使用单调时钟。

### 8.3 历史实验

历史行情回放及回测不得使用模拟时刻之后才可获得的数据。

不得使用尚未结束的 K 线最终收盘价进行提前决策。

## 9. Exchange Integration — 交易所接口规范

### 9.1 官方文档

接入交易所前必须调查：

- 官方 API 文档。
- 支持的市场类型。
- 支持的交易对。
- REST Endpoint。
- WebSocket Endpoint。
- 访问频率限制。
- 地区访问限制。
- 心跳机制。
- 错误码。
- 时间戳定义。
- 订单簿同步机制。
- 数据使用许可。

调查结果记录于：

```text
docs/03-EXCHANGE-API-RESEARCH.md
```

不得根据其他交易所的接口行为推断当前交易所行为。

### 9.2 接口权限

项目仅使用公开行情接口。

禁止：

- 调用真实下单接口。
- 调用真实提现接口。
- 创建具有真实交易权限的 API Key。
- 请求用户提供钱包私钥或助记词。
- 绕过交易所地区访问限制。
- 绕过交易所 API 限流。

接口无法访问时，应记录实际错误并选择合规替代数据源。

### 9.3 REST API

必须实现或明确配置：

- 请求超时。
- 错误处理。
- 限流控制。
- 有限次数重试。
- 指数退避。
- 请求结果记录。

不得无限重试。

不得对明确的权限、地区限制或参数错误进行无意义的持续重试。

### 9.4 WebSocket

必须考虑：

- 连接建立。
- 订阅确认。
- 心跳。
- 断线检测。
- 自动重连。
- 重新订阅。
- 重复数据。
- 乱序数据。
- 数据过期。
- 连接资源释放。

对于增量订单簿，还应考虑：

- 初始快照。
- Sequence ID。
- 增量更新。
- 数据缺口检测。
- Checksum 校验（交易所支持时）。
- 状态失效后的重新同步。

交易所之间的具体同步规则可能不同，必须遵循对应官方协议。

## 10. Testing Standards — 测试规范

### 10.1 测试分类

| 类型 | 目的 |
|---|---|
| Unit Test | 验证独立计算及数据转换逻辑 |
| Integration Test | 验证模块间协作 |
| API Smoke Test | 验证真实公开接口可用性 |
| Data Quality Test | 验证数据质量 |
| Stability Test | 验证持续运行能力 |

### 10.2 核心测试范围

必须覆盖：

- Decimal 数值计算。
- 数据模型校验。
- 交易对标准化。
- 时间戳转换。
- 缺失字段处理。
- 异常价格处理。
- 毛价差计算。
- 净收益估算。
- 行情过期检测。
- 接口异常处理。
- 订单簿同步及失效处理。

### 10.3 边界测试

至少考虑：

- 零值。
- 负数。
- null。
- 极大数值。
- 极小数量。
- 高精度价格。
- 重复消息。
- 乱序消息。
- API 超时。
- HTTP 429。
- WebSocket 断线。
- 数据格式变更。
- 交易对不存在。

### 10.4 真实接口测试

真实接口测试应与普通单元测试分离。

普通测试不得默认依赖外部网络。

真实接口测试必须：

- 明确数据源。
- 记录实际测试时间。
- 记录请求结果。
- 遵守访问限制。
- 保留必要的验证证据。

未执行真实接口测试时，不得声称已经通过实际接口验证。

### 10.5 测试结果

不得：

- 删除失败测试以获得通过结果。
- 修改预期值以掩盖实现错误。
- 跳过失败测试且不说明原因。
- 将未执行的测试标记为通过。

必须报告实际通过、失败、跳过及未执行的测试情况。

## 11. Security & Privacy — 安全规范

### 11.1 敏感信息

不得将以下信息写入 Git：

- API Secret。
- 私钥。
- 助记词。
- 密码。
- Access Token。
- 用户个人敏感信息。

即使当前阶段不使用认证信息，也应提前配置合理的 .gitignore。

### 11.2 外部输入

所有交易所响应及外部文件均视为不可信输入。

必须执行必要的数据校验。

不得执行外部响应中包含的任意代码或命令。

### 11.3 日志

日志不得泄露敏感信息。

日志应包含必要的：

- 时间。
- 交易所标识。
- 模块名称。
- 日志等级。
- 错误类型。
- 请求或实验标识。

避免将大量高频行情直接输出至普通运行日志。

## 12. Storage & Performance — 存储与性能

### 12.1 Phase 0 存储

优先使用：

- JSONL 保存行情及事件数据。
- CSV 保存统计及分析结果。
- JSON 保存实验配置。

暂不引入数据库。

### 12.2 存储容量

连续数据采集前必须：

- 估算每秒数据量。
- 估算每日文件大小。
- 设置存储容量限制。
- 设置文件轮换策略。
- 设置安全停止条件。

不得进行无容量限制的持续数据采集。

### 12.3 性能原则

- 优先保证数据正确性。
- 避免无必要的高频 REST 请求。
- 优先使用交易所支持的 WebSocket 订阅。
- 使用有界队列。
- 避免无限增长的内存集合。
- 正确处理采集速度与写入速度不匹配的问题。
- 记录丢弃数据及数据缺口。
- 避免阻塞异步事件循环。

不进行缺乏实际数据依据的提前性能优化。

## 13. Git Workflow — Git 管理规范

### 13.0 分支管理

- Repository：git@github.com:DaveSteven/crypto-lab.git
- 主要开发分支：`develop`
- 稳定版本分支：`main`
- Phase 0 默认在 `develop` 分支进行开发。
- 每次开发前必须确认当前分支及工作区状态。
- 不得直接在 `main` 分支进行功能开发。
- 不得未经授权创建、切换、合并或删除分支。
- 项目负责人已授权：每个 Task 通过相关测试及验收后，自动创建对应的本地 Commit。
- Push 或 Merge 仍须项目负责人逐次明确授权。
- 阶段性验收通过后，由项目负责人决定是否合并至 `main`。


### 13.1 基本原则

每次修改前检查：

```bash
git status
git branch --show-current
git diff
git diff --cached
```

确认是否存在用户已有的修改。

不得覆盖与当前任务无关的未提交内容。

### 13.2 禁止操作

未经明确授权不得：

- 执行 git reset --hard。
- 执行 git clean -fd。
- 强制覆盖远程分支。
- 删除分支。
- 修改既有提交历史。
- 执行 force push。
- 擅自向远程仓库提交代码。
- 删除用户已有的未提交文件。

### 13.3 Commit 规范

建议采用 Conventional Commits：

```text
feat: add exchange REST API adapter
fix: handle invalid order book snapshots
docs: update phase 0 research findings
test: add spread calculation tests
refactor: simplify market data normalization
chore: initialize python project
```

每次提交应聚焦单一任务或一组具有明确关联的修改。

完成 Task 并通过相关测试及验收后，自动创建本地 Git Commit。

不得把多个尚未完成或互不相关的 Task 混入同一 Commit。若项目初始化阶段因历史原因尚无基线 Commit，可在记录范围后创建一次基线 Commit。

未经用户逐次明确授权，不得执行 Git Push。

### 13.4 数据文件管理

以下内容原则上不提交至 Git：

- 大量原始行情数据。
- 连续采集产生的日志。
- 临时实验文件。
- Python 虚拟环境。
- 缓存文件。
- 本地敏感配置。

用于自动化测试的小型固定样本可纳入版本管理。

## 14. Documentation Standards — 文档规范

### 14.1 文档语言

- 项目文档优先使用中文。
- 技术术语保留英文。
- 源代码标识符使用英文。
- 代码注释根据实际需要编写，避免重复描述代码。

### 14.2 文档维护

以下情况必须更新相关文档：

- 新增数据源。
- 修改 API 接入方案。
- 修改数据结构。
- 修改核心金融公式。
- 修改实验参数。
- 修改运行方式。
- 完成技术验证。
- 发现接口限制。
- 发生重要架构变更。

### 14.3 事实状态

调查及研究内容应区分：

- Verified：已经实际验证。
- Documented：来自官方文档，尚未实际验证。
- Assumed：当前设计假设。
- Failed：实际验证失败。
- Pending：尚待调查。

不得将 Assumed 或 Pending 描述为 Verified。

### 14.4 架构决策记录

重要架构决策保存于：

```text
docs/decisions/
```

每份 ADR 至少包含：

- 背景。
- 问题。
- 候选方案。
- 最终决定。
- 决策原因。
- 影响范围。
- 当前状态。

## 18. Core Directive — 核心指令

本项目首先是一个金融学习及研究工具，其次才是一个软件产品。

职责原则：AI 负责开发和解释，程序负责采集和计算。

- AI 负责需求分析、方案设计、代码实现、测试、结果解释及风险说明。
- 采集程序负责按配置持续获取数据、执行确定性计算并生成结构化统计报告。
- AI 不通过长时间占用会话或持续轮询来代替采集程序。
- 程序输出的统计结果必须保留配置、时间范围及数据来源，供后续独立分析。

开发工作的价值不在于实现尽可能多的功能，而在于：

- 获取可信的数据。
- 建立正确的金融模型。
- 验证真实的市场规律。
- 发现策略的局限性。
- 建立可复现的实验环境。
- 帮助项目负责人理解市场。

当开发速度、功能数量与数据真实性发生冲突时，优先保证数据真实性。

当模拟收益与真实市场约束发生冲突时，优先保证真实市场约束。

当实现结果与已确认的需求发生冲突时，优先定位并解决冲突。

不确定的事实必须标记为不确定。

未验证的结果必须标记为未验证。

## 19. Token Efficiency & Long-running Tasks — Token 效率与长时间任务

- 默认真实接口验证时间为 15 秒。
- 默认多交易所采集测试时间为 60 秒。
- 稳定性测试默认不超过 300 秒。
- 超过 300 秒的采集任务应独立执行，不阻塞 AI 开发会话。
- 禁止持续轮询长时间运行的采集进程。
- 禁止将高频行情逐条输出至终端。
- 原始行情数据应写入本地文件。
- 采集程序必须自动生成结构化统计报告。
- 优先使用 Python 完成统计及数据分析。
- AI 优先读取统计报告，仅在排查异常时读取必要的原始数据样本。
- 禁止无必要地读取完整的大型 JSONL 文件。
- 所有采集脚本必须支持运行时长、存储容量及日志等级配置。
- 短时功能测试与长期稳定性实验必须分离。
- 不得以短时测试通过代替长期稳定性验收。
- 长期实验结束后，由项目负责人发起独立的实验结果分析任务。
